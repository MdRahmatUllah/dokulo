# DK-1044 · PDFium lane runs through pdfrx's worker; reset a failed PDFium spawn (DK-0007 follow-up)

Added by agent-0, 2026-10-07 22:45.

From agent-2's H-115 and agent-1's review of #433.

Problem: pdfrx_engine runs every PDFium call on a BackgroundWorker isolate that is a singleton per Dart isolate. The viewer (DK-0293) uses pdfrx from the UI isolate (worker #1); a job on IsolatePool's own Lane.pdfium isolate that touches pdfrx starts worker #2: two threads in PDFium, which is not thread-safe.

Fix: Lane.pdfium runs the job body on the calling isolate; every PDFium call goes through pdfrx (its API, PdfrxEntryFunctions.instance.compute, or PdfDocument.useNativeDocumentHandle for raw FPDF_* calls), so it is serialised with the viewer on pdfrx's one worker. No other native call runs on the calling isolate (assertWorkerIsolate stays for qpdf/OpenCV/ONNX bindings). Cancel stays cooperative (checkCancelled between pages). Also: a failed Isolate.spawn must not stick (reset the cached worker).

Acceptance: IsolatePool tests updated (PDFium jobs run on the calling isolate; cancel within 1 s; temp freed); a failed spawn is retried on the next job; Developer guide §1 and the IsolatePool doc comment say how PDFium is reached.
